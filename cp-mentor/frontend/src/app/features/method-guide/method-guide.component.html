A complete method, with worked examples. Java-oriented. Built for product-company interview preparation.

Part 0

psychology_altThe Mindset Shift

On a first attempt, your goal is not to solve the problem. Your goal is to produce two artefacts:

  1. A working brute force.
  2. One sentence stating exactly why it is too slow.

If you have both, the attempt succeeded — even if you never reached the optimal solution.

Why this matters: "I couldn't solve it" is a demoralising and useless signal. "I found the O(n²), and the bottleneck is that I recompute the same suffix maximum at every index" is precise and fixable. It is also literally what interviewers score. Nobody expects instant optimal. They expect structured progress from a stated starting point.

The second reframe, equally important:

Never model the physics. Model the computation. Beginners get stuck on Trapping Rain Water because they imagine water flowing and pooling. Water does not flow in your program. Your program sums numbers. The moment you switch from "how does water behave" to "what number do I compute at each index," the problem collapses.

rulePhase 0 — Constraints First

This is the single most underused technique on LeetCode. Constraints leak the intended complexity before you read a word of the problem.

Constraint on nIntended complexityTypical technique
n ≤ 10-12O(n!)Permutations, full backtracking
n ≤ 20-25O(2ⁿ)Bitmask DP, subset enumeration
n ≤ 100-500O(n³)Interval DP, Floyd-Warshall, matrix chain
n ≤ 2,000-5,000O(n²)2D DP, all-pairs comparison
n ≤ 10⁵-10⁶O(n log n) or O(n)Sort, heap, two pointer, sliding window, hashing
n ≤ 10⁹O(log n) or O(1)Binary search on the answer, maths, bit tricks
n ≤ 10¹⁸O(log n)Matrix exponentiation, digit DP, number theory

Also extract from the constraints:

  • Can values be negative? → kills many greedy and prefix-sum shortcuts
  • Can values be zero? → division-based tricks die
  • Are values bounded and small (e.g. 0 <= v <= 100)? → counting sort, frequency array of fixed size, bitset
  • Is the array sorted? → two pointer and binary search are immediately live
  • Are elements distinct or can they repeat? → changes almost every two-pointer implementation
  • What is the minimum n? n >= 1 versus n >= 0 changes your guard clauses

Write the target down before continuing. Literally type it as a comment:

// n <= 2*10^4 -> O(n^2) = 4*10^8, too slow. Need O(n) or O(n log n). // height[i] can be 0. n can be 1.

chat_bubble_outlinePhase 1 — Restate and Brute Force

Restate the problem in one sentence, in your own words.

If you cannot, you have misread it. Misreading is a top-three cause of wasted hours and it is invisible until you have already lost forty minutes.

Bad restatement: "Find the water."
Good restatement: "For each index, compute how much water sits directly above that bar, and return the sum."

Notice the good restatement already contains the algorithm's shape.

Then state a brute force out loud, however absurd. You should never be at zero. Enumerate everything and check each candidate. If the brute force is O(n!), say so and move on — you have still established a baseline and, more importantly, a definition of correctness you can test the fast solution against.

Diagnostic: if you cannot even state a brute force, you almost always have the wrong unit of analysis. Go straight to Phase 2.

editPhase 2 — Solve a Tiny Case By Hand

Take n = 4 or 5. Get out paper. Produce the answer manually.

On paper, not in your head. In-head reasoning skips steps and hides exactly the insight you are looking for.

Then ask the question that does the work:

What did my brain actually just do?

Your hand-method is usually the algorithm in disguise. Examples:

ProblemWhat your hand doesThe algorithm
Next PermutationScan right-to-left looking for the first dipExactly the algorithm
Trapping Rain WaterLook left and right of each hole for wallsPrefix max and suffix max
Valid ParenthesesCross off matched pairs inwardsStack
Merge IntervalsSort them mentally, then glue overlapsSort + linear merge
Two SumRemember what you have seen so farHash map

If your hand-method is genuinely brute force (you checked all pairs), that is information too — it means the insight is not in the problem's surface and you will need Phase 3 to find it.

boltPhase 3 — Name the Bottleneck, Run the Five Moves

Ask exactly one question:

What am I recomputing?

Answer it precisely, not vaguely.

Vague and useless: "the maximums."
Precise and actionable: "when I move from index i to i+1, I re-scan almost the identical left portion of the array to find a value I already computed one step ago."

The precise version basically names its own fix.

Then run this checklist explicitly. Around 90% of mediums fall to one of these five.

Move 1 — Store instead of recompute

The value you need was already computed; save it.

Techniques: hash map, prefix sum, prefix/suffix arrays, memoisation, frequency counts.

Examples: Two Sum, Subarray Sum Equals K, Product of Array Except Self, Trapping Rain Water, Longest Consecutive Sequence, every top-down DP.

Trigger: "I keep re-scanning the same region."
Move 2 — A pointer or window never needs to move backwards

If expanding the window can only ever help and shrinking is monotonic, you get O(n) instead of O(n²).

Techniques: two pointer, sliding window (fixed and variable), fast/slow pointer.

Examples: Longest Substring Without Repeating Characters, Minimum Window Substring, Container With Most Water, Remove Duplicates, Linked List Cycle.

Trigger: "contiguous subarray/substring" + "longest / shortest / at most K."
Move 3 — Sort first, then the structure becomes exploitable

Sorting costs O(n log n) but often turns an O(n²) search into an O(n) sweep.

Techniques: greedy after sort, two pointer on sorted array, sweep line, interval merging.

Examples: Merge Intervals, 3Sum, Meeting Rooms II, Non-overlapping Intervals, Minimum Number of Arrows.

Warning: sorting destroys original indices. If the answer requires indices, store pairs or use a different move.
Move 4 — Only the max/min matters, not the whole set

You are carrying a whole collection when you only ever query one end of it.

Techniques: heap / PriorityQueue, monotonic stack, monotonic deque, running max/min variables.

Examples: Kth Largest, Merge K Sorted Lists, Next Greater Element, Largest Rectangle in Histogram, Sliding Window Maximum, Task Scheduler.

Trigger: "next greater / previous smaller" → monotonic stack. "top K" / "K-th" → heap.
Move 5 — The answer is monotonic in some parameter

If "can I achieve X?" is easy to check, and being able to achieve X implies being able to achieve X+1, binary search the answer.

Techniques: binary search on answer space, not on the array.

Examples: Koko Eating Bananas, Split Array Largest Sum, Capacity to Ship Packages, Minimise Max Distance to Gas Station, Median of Two Sorted Arrays.

Trigger: "minimise the maximum" or "maximise the minimum."

Beyond the five

If none of the five fit, ask these in order:

  • Does the problem have overlapping subproblems and optimal substructure? → DP. Then define the state as a sentence: "dp[i][j] = the best answer considering the first i items with j capacity remaining." Never write DP code before you can say that sentence.
  • Are there entities and relationships? → graph. Then decide: shortest path (BFS/Dijkstra), connectivity (DSU/DFS), ordering (topological sort), or cycle detection.
  • Does a local greedy choice provably never hurt? → greedy. You must be able to argue why, or you will fail on a counterexample.
  • Is it about individual bits, or n ≤ 25 with subsets? → bit manipulation.

codePhase 4 — Code

If you did not finish Phase 3 with a clear plan, do not start typing. Coding while confused is how a 30-minute problem becomes a two-hour problem.

Before the first line, write two comments:

// Approach: <one sentence> // Time: O(?) Space: O(?)

Java-specific habits that show up in interview feedback:

  • Use int mid = lo + (hi - lo) / 2; — never (lo + hi) / 2, which overflows.
  • long for sums that can exceed 2³¹, which happens more often than you think.
  • Name variables for meaning: leftMax, writeIndex, windowStart — not a, temp, x. Interviewers grade this.
  • Prefer int[] over List<Integer> in hot loops; autoboxing is a real cost.
  • HashMap.getOrDefault(key, 0) and map.merge(key, 1, Integer::sum) keep frequency code short.
  • Deque<Integer> stack = new ArrayDeque<>(); — not Stack, which is legacy and synchronised.
  • Arrays.sort() on int[] is dual-pivot quicksort with O(n²) worst case; on Integer[] it is stable TimSort. This distinction has been an actual interview question.

Run this checklist mentally, every time:

  • check_box_outline_blankMinimum input: n = 1, or the empty case if permitted
  • check_box_outline_blankAll elements identical
  • check_box_outline_blankAll negatives (if values can be negative)
  • check_box_outline_blankAlready sorted, and sorted in reverse
  • check_box_outline_blankDuplicates present

  • check_box_outline_blankThe answer is at the very first or very last index

Getting a wrong-answer verdict you could have predicted costs you the debugging time and the confidence. Both are expensive.

Part 3

stairsThe Stuck Ladder

Never jump to the editorial. Climb one rung at a time and stop the moment something unlocks.

  1. Re-read the constraints. (2 min) You skipped Phase 0 more often than you would like to admit. The complexity target is itself a hint: O(n) rules out any nested loop, which sharply constrains the shape of the answer.
  2. Try a differently-shaped example. (5 min) Not a bigger one — a weirder one. All duplicates. Sorted descending. All negatives. n = 1. Values equal to zero. The counterexample that breaks your current idea usually reveals the correct one.
  3. Name the family, do not find the solution. (5 min) Ask only: which pattern is this? Two pointer, sliding window, binary search, prefix sum, hashing, monotonic stack, heap, greedy, DP, backtracking, graph traversal, union-find, bit manipulation, intervals, maths. Guessing the family narrows the search space enormously without spoiling the derivation.
  4. Look at the LeetCode tags only. Open the tags, read nothing else, close the tab. This is a controlled hint: it confirms the family and preserves the derivation, which is the part that actually builds skill.
  5. Ask for a Level 1 or Level 2 hint. Level 1 is a single observation. Level 2 names the pattern and explains why it fits. Both leave the real work with you.
  6. Read the solution, and stop reading the instant you understand. The moment the key idea lands, close the tab. Do not read the code. Do not read the complexity analysis. You have the idea; implementing it is your job, and implementing it is where retention comes from.
Part 4

restoreThe Recovery Protocol

Reading a solution teaches you almost nothing. Solving problems and then forgetting them happens because reading feels like learning. It is not. Here is what converts a read solution into a retained one.

  1. Close everything. Every tab, every note.
  2. Wait 10 minutes. Do a different problem, get water, walk around.
  3. Re-implement from a blank editor, no reference. If you cannot, you did not learn it — go back to the idea, not the code.
  4. Log the missed observation. Not the solution. The single thing you failed to notice.
  5. Re-solve at Day+2 and Day+7. The problem counts as genuinely solved only after the Day+7 re-solve succeeds.

Parts 7–9

scienceWorked Examples

Trapping Rain Water
LC 42 · Hard

Phase 0 — Constraints

n == height.length 1 <= n <= 2 * 10^4 0 <= height[i] <= 10^5

n = 2×10⁴ → O(n²) ≈ 4×10⁸ operations, over budget. Target O(n) or O(n log n). height[i] can be 0. n can be 1, so a single bar must return 0 without crashing.

Phase 1 — Restate and brute force

Here is what makes this problem an excellent diagnostic: most people cannot state a brute force. They picture water flowing, pooling, levels rising — and freeze.

That freeze is the signal. It means the unit of analysis is wrong. You are modelling physics, not computation.

Phase 2 — Hand-solve

Take height = [3, 0, 2, 0, 4]. Compute the water manually.

You did not simulate flowing water. You went position by position and asked "how high can water sit here?", answering it by looking left and right for walls.

That is the reframe: do not ask how much water the terrain holds. Ask how much water sits on top of each individual bar, then sum. Water decomposes into vertical columns, not pools.
water[i] = min( max(height[0..i]), max(height[i..n-1]) ) - height[i] answer = sum of water[i], clamped at 0

Phase 3 — Bottleneck

Brute force from that formula: for every index, scan left for max, scan right for max. O(n²) time, O(1) space. Correct, but over budget.

What am I recomputing? Precisely: moving from index i to i+1, I re-scan an almost identical left portion to find a value I computed one step ago.

Five moves:

  • 1. Store instead of recompute → leftMax[i] relates to leftMax[i-1] by a one-line rule. ✅ This lands.
  • 2. Window never moves backwards → not obvious yet.
  • 3. Sort first → destroys position, and position is the entire problem. ✗
  • 4. Only max/min matters → interesting; hold this thought.
  • 5. Binary search on answer → no monotonic parameter. ✗

Move 1 gives O(n) time, O(n) space: build a prefix-max array and a suffix-max array in two passes, then one final pass applying the formula.

Phase 4 and 5

Code it. Dry run [5], [1,2,3,4] (answer 0 — a classic index-bug catcher), [3,3,3], [4,2,0,3,2,5] (answer 9).

The follow-up

An interviewer seeing O(n) time / O(n) space will ask for O(1) space. Return to move 4, which you set aside. Hint, no more: with two pointers at opposite ends, if you know the left max is smaller than the right max, is there anything the right side could still tell you about the left pointer's water level?

Do not chase this until the O(n)-space version is green. One working solution beats two half-built ones.

LC 42 — Trapping Rain Water Trigger: answer at index i depends on a prefix aggregate AND a suffix aggregate Missed: decompose per column, not per pool Family: prefix/suffix precomputation -> two pointer for O(1) space Reuse in: Product of Array Except Self, Candy, Best Time to Buy and Sell Stock III
Koko Eating Bananas
LC 875 · Medium — a deliberately different family, to show the method generalises

Phase 0 — Constraints

1 <= piles.length <= 10^4 piles.length <= h <= 10^9 1 <= piles[i] <= 10^9

Two things jump out. piles[i] up to 10⁹ means the answer space is huge even though the array is small. And h up to 10⁹ means any solution that iterates over hours is dead.

When the array is small (10⁴) but the value range is enormous (10⁹), that mismatch is itself the hint: you are searching over values, not over positions.

Phase 1 — Restate and brute force

Restated: "Find the smallest eating speed k such that finishing all piles at k bananas per hour takes at most h hours."

Brute force: try k = 1, 2, 3, ... up to max(piles). For each, compute hours needed. Return the first k that fits. O(max(piles) × n) = 10⁹ × 10⁴. Absurdly slow, but it is a baseline and it defines correctness.

Phase 2 — Hand-solve

piles = [3, 6, 7, 11], h = 8.

  • k = 1 → 3 + 6 + 7 + 11 = 27 hours. Too slow.
  • k = 2 → 2 + 3 + 4 + 6 = 15. Too slow.
  • k = 3 → 1 + 2 + 3 + 4 = 10. Too slow.
  • k = 4 → 1 + 2 + 2 + 3 = 8. Fits.
  • k = 5 → 1 + 2 + 2 + 3 = 8. Also fits.

Answer: 4.

What did your hand notice? Hours needed only ever decreases as k increases. Once a speed works, every faster speed also works.

Phase 3 — Bottleneck

What am I recomputing? I am testing every k one at a time, when the results have a monotonic structure I am ignoring.

  • 1. Store instead of recompute → nothing repeats meaningfully. ✗
  • 2. Window never moves backwards → not a window problem. ✗
  • 3. Sort first → order of piles is irrelevant to the answer. ✗
  • 4. Only max/min matters → not quite. ✗
  • 5. The answer is monotonic in a parameter → ✅ k works ⟹ k+1 works.

Binary search over k in the range [1, max(piles)]. Each check is O(n). Total O(n log(max piles)) ≈ 10⁴ × 30. Trivially fast.

The key structural insight, and the one worth logging: you are binary searching the answer space, not the input array. The array is never sorted at all.

Java gotcha

Hours for one pile is ceil(pile / k), which in integer arithmetic is (pile + k - 1) / k. Accumulate into a long — with 10⁴ piles of 10⁹ each and k = 1, the sum overflows int immediately. This exact overflow is the most common wrong-answer on this problem.

Longest Substring Without Repeating Characters
LC 3 · Medium — compressed walkthrough

Phase 0: n ≤ 5×10⁴ → need O(n). Characters include digits, symbols, spaces — do not assume lowercase-only.

Phase 1: Restate: "the longest contiguous stretch with no character appearing twice." Brute force: check every substring for uniqueness, O(n³), or O(n²) with an incremental set.

Phase 2: On "abcabcbb" by hand, you extend right until you hit a repeat, then you move the left edge past the previous occurrence of that character — you never move left backwards.

Phase 3: Bottleneck: I re-check characters already known to be unique. Move 2 fires — the left pointer is monotonic. Move 1 also fires — a hash map storing the last index of each character makes the left jump O(1) instead of a scan. Result: O(n) time, O(min(n, alphabet)) space.

Trigger: "longest contiguous stretch satisfying a constraint" → variable-size sliding window.

Edge cases: empty string, all identical characters, all distinct, a single space.

Part 10

record_voice_overInterview Communication Script

Everything above is also your talk track. In a real interview, narrate the phases out loud — that narration is the signal being graded.

  1. "Let me check the constraints first. n is up to 10⁵, so I'm targeting O(n log n) or better."
  2. "Let me restate to make sure I have it: ..."
  3. "The brute force would be ... which is O(n²). Let me confirm that's correct, then optimise."
  4. "Let me trace a small example to find the structure." — and actually write it on the board.
  5. "The bottleneck is that I recompute ... at every step. I can store that instead."
  6. "Approach: ... Time O(n), space O(n). Shall I code it?"
  7. Code, then: "Let me trace it on the example, and check the edge cases: empty, single element, all duplicates."
  8. "For the follow-up on space, I think we could ..."
Never go silent. Silence is the only unrecoverable interview failure. If you are stuck, say what you have tried and what you have ruled out — that is still visible progress.
